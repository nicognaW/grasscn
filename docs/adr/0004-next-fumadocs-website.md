# Adopt Next.js and Fumadocs MDX for the website

Migrate the website and documentation to Next.js with Fumadocs and MDX, following relevant shadcn/ui and 8bitcn architecture and conventions while retaining Grasscn's Minecraft visual identity and component demos. Improve documentation completeness alongside the framework migration using the [upstream completeness research](../audits/next-mdx-documentation-completeness-2026-11-01.md): each component page provides a small runnable example with matching copyable code, CLI/manual installation, actual usage/composition guidance, relevant named examples and useful API/accessibility/limitations notes. Keep existing interactive playgrounds as additional examples, describe actual supported Grasscn behavior and link to dependency APIs where appropriate.

Distinguish executable example code from installable component implementation source. Manual installation identifies dependencies and destination paths for every required file, including helpers, styles and resources; provide selectable, copyable and downloadable complete source, loading large resources on demand. Visitor installation commands offer npm, pnpm, Yarn and Bun, remember the selected manager and copy its actual command; repository development remains pinned to Bun.

Assume visitors are already proficient with shadcn and use existing shadcn-ready projects. Document Grasscn-specific setup requirements, dependencies, styles/resources, usage and differences; link to authoritative upstream documentation for shared material instead of reproducing generic framework setup, SSR, skills, registry or shadcn tutorials. Mention framework or server/client details only when needed for a concrete Grasscn requirement. This audience scope preserves complete per-component manual installation and independent Next/Vite consumer verification; it removes the earlier requirement for general Next.js/Vite setup guides.

Use headless Fumadocs core and MDX beneath Grasscn's own fully Minecraft-styled UI. Fumadocs owns the documentation content pipeline in place of the bespoke documentation generation system; adopting Fumadocs does not introduce its stock UI or change the existing primitive dependency policy. Registry distribution and captured-reference evidence retain their own authoritative inputs.

The entire new site has a hard Minecraft pixel-perfect goal, including rendered documentation content, examples, newly required website controls such as package-manager switches, and the overall visual presentation. Reuse faithful UI ports, original assets and measured rendering rules; new or extended native elements follow the UI-port workflow and zero-differing-RGBA acceptance for declared captured-reference cases in the integrated site. Website-only layouts and functions remain identified as web adaptations composed of faithful elements, with desktop/mobile visual evidence for the overall presentation; they do not justify generic framework styling or unsupported whole-page native claims. Missing native evidence is an explicit acceptance gap, not permission to lower the goal to visual similarity.

Build the new website directly from the Next.js and headless Fumadocs architecture, using old website code as reference for appearance, content and behavior. Do not first make the old website run inside Next or introduce a temporary legacy documentation adapter as a migration stage. Preserve agreed product behavior and independent registry/evidence responsibilities in the new implementation; sequence new-site capabilities on an integration branch with complete acceptance at final integration, rather than requiring an old-site compatibility stage.

Use Fumadocs search for documentation text and headings while preserving discovery by component name, alias and public export. Retain Grasscn's Minecraft search interface and keyboard interaction. Derive the documentation sidebar from the Fumadocs page tree and the table of contents from MDX headings, rendering both with Grasscn's Minecraft-styled UI; preserve homepage and chart-showcase layouts.

Follow upstream documentation routing under `/docs`, with a canonical page at `/docs/components/<name>` for every installable registry item. Cross-link related pages and share examples where useful, replacing the old grouped-page aliases with independently discoverable documentation. Chart has installation/API documentation as well as its existing `/charts` showcase. Preserve existing `/components/<name>` links through compatibility redirects, including relevant query parameters and section anchors; the homepage and chart showcase remain outside the docs tree.

Use the ordinary Next.js development, build and production-server model under Bun, aligning with shadcn/ui and 8bitcn rather than requiring a static export. Prerender MDX documentation where appropriate and serve documentation search through Next; public hosting is a separate decision. Bun runtime compatibility must be demonstrated during implementation.

Use Next's supported Webpack bundler for production and development. Fumadocs supplies a custom Webpack configuration, so explicitly enable `experimental.webpackBuildWorker`: Next otherwise compiles in its main process and retains that compiler heap during prerendering. Next runs these compiler workers serially and ends each before the next stage. Keep the pinned Bun runtime, its documented `--smol` production option, Next's type checking and normal prerendering. The measured build rationale and unsuccessful resource probes are recorded in the final integration audit; development and consumer compatibility still require their own runtime evidence.

Composed verification may explicitly reuse a completed production build. Its receipt must record the observed successful command and match the current source, Bun/platform/locale/time zone, installed dependency bytes, generated MDX/types/environment inputs and delivered Next/registry bytes. A missing, interrupted or changed build requires fresh preparation. Ordinary verification still runs every non-PPT check; explicitly selected Base PPTs retain their separate purpose and Full authorization policy.

Validate documentation at the visitor's consumer boundary: build and typecheck documented examples, exercise copied examples and manual installation in independent Next and Vite consumers, and cover representative simple, composed and resource-heavy manual installations. Retain the all-item real-CLI installation check. Run all ordinary browser checks for docs navigation, search, preview/code switching, copying and file selection alongside existing component behavior checks, plus explicitly chosen Base PPTs; Full PPTs retain their separate approval policy. A page containing the expected headings is insufficient evidence that its instructions produce a working consumer.

When presenting a PR as ready for acceptance or merging, provide a running local preview link for the user, including links to the relevant pages and controls. Serve the actual proposed source snapshot on loopback; a draft PR link, build result or superseded website process is not a substitute for the acceptance preview.

This is a separate migration built on the completed Bun/Turborepo work in issue #5. ADR 0003 deliberately retains Vite for the Bun migration and leaves this subsequent framework change independent; this decision replaces that website framework choice after the Bun migration, preserving its workspace and toolchain responsibilities and the captured-reference and Base/Full contracts in ADRs 0001 and 0002. Markdown export, full-screen previews, AI integrations and exhaustive upstream example parity remain deferred.
