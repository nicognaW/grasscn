# Website architecture and acceptance

The supported website is the Next.js App Router application in `apps/web`, running under pinned Bun. Headless Fumadocs MDX owns authored content, page metadata/tree, headings/TOC and search. Author explanations in `content/docs`; maintain runnable consumer examples in `examples`. Preview code is example code; implementation and manual files come from authoritative registry metadata. Registry symbol and evidence adapters have separate authoritative inputs.

The Vite application in `packages/tests/fixtures/renderer` remains an independent component fixture. Retained `apps/web/demos` are additional interactive playgrounds rendered by canonical documentation pages. Preserve their support data, resource provenance and public behavior. Use current package scripts for generation, development, build and production commands; Turbo orders generation and registry delivery before Next output, while direct Uncheck discovers workspace checks after generation.

The public development and production scripts select Next's supported Webpack bundler. Fumadocs' custom Webpack configuration requires explicitly enabling Next's separate build worker to release compiler heaps before prerendering. Bun remains the runtime; production uses its documented `--smol` memory mode. See ADR0004 and the integration audit for measured evidence and remaining runtime gates.

The web tasks prepend `--smol` through documented `BUN_OPTIONS` so Windows' native `next.exe` launcher and Next's server forks receive the runtime setting. Turbo declares this environment input explicitly, preserving strict mode and invalidating cache keys when it changes. Prepared build, installed-toolchain and consumer phase identities bind its hash. Development disables Webpack's filesystem cache to avoid measured pack-serialization memory spikes; production Webpack and Turbo caching remain enabled. Grasscn's code viewer owns syntax highlighting; Fumadocs' optional fence-highlighting pass is disabled through its native configuration while its content, headings, TOC and search remain authoritative.

Maintainer verification owns a Bun Next production process, rejects occupied ports and binds its source/build/public-registry identity separately from the fixture bundle. `next-production.mjs` stamps a completed build and starts only unchanged source/output. Source, dependency, content/config and artifact changes invalidate matching checkpoints. Verification tasks are uncached; deterministic Turbo outputs may restore from matching cache keys.

For composed normal/PPT preparation, `GRASSCN_REUSE_PREPARED_NEXT_BUILD=1` explicitly consumes an already completed production receipt through the shared `readPreparedProductionBuild` interface. It verifies the successful command, source, runtime environment, installed dependency bytes, generated inputs and delivered output before reusing that one stage. Missing or changed receipts fail; the default preparation runs its build. Development verification restores the prior generated MDX/environment inputs after checking fresh dev output and retains its generated versions as artifacts.

Manual-consumer verification uses fresh projects physically outside the repository and its workspace ancestors. Copy actual visitor-visible examples and download every required manual file; observe composed interactions, loaded resources and WebGL readiness in both Next and Vite. The separate all-item shadcn CLI check starts its own external consumer and installs actual current public `/r` URLs. Check dependency realpaths and installed bytes to exclude inherited repository modules.

All normal unit, API and browser behavior tests belong to `packages/tests` and run ordinarily without a Base/Full gate. Read `test-classification.md` before changing PPT mappings in `packages/pixel-perfect`. Base PPT execution is an explicit choice; Full PPT authorization, independent execution and nonblocking results remain unchanged. Complete inventory listing is read-only. Shared runtime and consumer helpers expose public interfaces to specialized PPT callers; normal consumers never import PPT policy or run native comparisons automatically. Captured-reference bytes and declared native conditions remain authoritative; page composition screenshots and fixture/consumer/site evidence have distinct scopes.

Before presenting acceptance, serve the actual proposed snapshot at `http://127.0.0.1:5176/` and provide direct homepage/charts/docs/control links. Keep process and source identity in verification artifacts rather than product UI. A build or draft PR alone does not replace a running acceptance preview.
